Pages vs Tests — Rules Cheatsheet

Selenium + Java + TestNG + Page Object Model  |  thndrbladers/FreeCrm

Rule 1 — Pages execute, Tests direct

The Page does the action. The Test decides when, with what data, and what to verify.
// ❌ Wrong — page is directing itself
public void fillAndSave(String file) {
  List<Object[]> data =
    new ExcelUtility(file).getExcelDataAsList();
  for (Object[] row : data) {
    firstNameInput.sendKeys(row[0].toString());
    saveButton.click();
  }
}
// ✅ Correct — page just executes
public void fillContactForm(
    String firstName, String lastName ...) {
  firstNameInput.sendKeys(firstName);
  lastNameInput.sendKeys(lastName);
}

public void saveContact() {
  saveButton.click();
}

Rule 2 — Pages never own data

Data is always passed in. Pages never read files, never hardcode values.
// ❌ Wrong — hardcoded data in page
public void fillForm() {
  firstNameInput.sendKeys("John");
}

// ❌ Wrong — page loads the file
public void fillForm(String file) {
  List<Object[]> data =
    new ExcelUtility(file).getExcelDataAsList();
}
// ✅ Correct — test loads data,
//             passes to the page

// In Test:
List<Object[]> data = new ExcelUtility(
  "TestData", filePath).getExcelDataAsList();

contactPage.fillContactForm(
  data[0][0].toString(),
  data[0][1].toString() ...);

Rule 3 — Pages never loop

Iteration is always the test's job. If you write a for loop in a page — move it to the test.
// ❌ Wrong — loop inside a page method
public void createMultiple(
    List<Object[]> rows) {
  for (Object[] row : rows) {
    createButton.click();
    firstNameInput.sendKeys(row[0].toString());
    saveButton.click();
  }
}
// ✅ Correct — loop lives in the test
for (Object[] row : data) {
  contactPage.clickCreate();
  contactPage.fillContactForm(
    row[0].toString(),
    row[1].toString() ...);
  contactPage.saveContact();
}

Rule 4 — Pages never assert

Pages only return values or booleans. The test decides what to do with them.
// ❌ Wrong — assertion inside the page
public void verifyContactInList(
    String name) {
  Assert.assertTrue(
    contactList.isDisplayed(),
    "Contact not found");
}
// ✅ Page returns state
public boolean isContactInList(
    String firstName, String lastName) {
  try {
    return getDriver().findElement(By.xpath(
      "//span[text()='" + firstName
      + " " + lastName + "']")).isDisplayed();
  } catch (NoSuchElementException e) {
    return false;
  }
}

// ✅ Test asserts it
sa.assertTrue(
  contactPage.isContactInList("John","Doe"),
  "AC5 FAILED: Contact not in list");

Rule 5 — Pages never navigate away from themselves

Never call another page's constructor silently inside a void method. The test decides where to go next.
// ❌ Wrong — navigates silently
public void saveContact() {
  saveButton.click();
  new HomePage().clickContacts();
  // who told this page to go back?
}
// ✅ Page only saves
public void saveContact() {
  saveButton.click();
}

// ✅ Test decides navigation
contactPage.saveContact();
homePage.clickContacts();

Rule 6 — If a click navigates, return the next Page Object

Never return void from a method that takes you to a new page.
// ❌ Wrong — navigates, returns nothing
public void clickContacts() {
  contactsMenu.click();
}
// ✅ Correct — returns where you land
public ContactPage clickContacts() {
  contactsMenu.click();
  return new ContactPage();
}

// Enables clean chaining in test:
ContactPage contactPage =
  new LoginPage()
    .login("user@mail.com", "Pass@1")
    .clickContacts();

Rule 7 — One method = one user intention

Multiple lines are fine if they serve ONE user intention. The "and" test — if you need "and" to describe it, split it.
// ❌ Wrong — "and" = two intentions
public void fillFormAndSave(...) {
  firstNameInput.sendKeys(firstName);
  saveButton.click();
}
// ✅ Split by intention
public void fillContactForm(...) {
  firstNameInput.sendKeys(firstName); ...
}
public void saveContact() {
  saveButton.click();
}

// ✅ login() — 3 lines, ONE intention
public HomePage login(
    String email, String password) {
  emailInput.sendKeys(email);
  passwordInput.sendKeys(password);
  loginButton.click();
  return new HomePage();
}

Where does this code live?

If it…Goes in
Touches the DOMPage
Loops over dataTest
Reads a file (Excel/CSV)Test calls Utility
Asserts somethingTest
Navigates to another pagePage (return next Page)
Is generic, no page contextUtility
Driver setup / teardownBase

The "and" test — split or keep?

DescriptionDecision
"I logged in"Keep — one intention
"I filled the form"Keep — one intention
"I filled the form and saved"Split into 2 methods
"I saved and navigated back"Split — nav in test
"I loaded data and filled form"Split — data in test
